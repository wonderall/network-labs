# Site-to-Site IPsec VPN 작동 로직 및 트러블슈팅 가이드

본 문서는 Cisco 라우터 간 구성된 **지점 간(Site-to-Site) IPsec VPN**의 핵심 작동 로직과 포트폴리오/보고서용 **단계별 검증 및 트러블슈팅(Troubleshooting) 명령어**를 정리한 기술 문서입니다.

---

## 🏢 1. IPsec VPN의 핵심 역할
* **사설망 간 통신 구현:** 사설 IP 대역(서울 본사 `192.168.10.0/24` ↔ 부산 지사 `192.168.20.0/24`)은 원래 인터넷을 통해 직접 통신할 수 없습니다. VPN은 공인 인터넷망 위에 안전한 **가상의 사설 지하 터널**을 뚫어 직접 통신을 가능하게 합니다.
* **보안성 확보:** 공인 인터넷망을 통과할 때 데이터를 강력한 암호 상자에 넣어 보내므로, 중간에서 해커가 데이터를 도청하거나 변조하는 것을 원천 차단합니다.

---

## ⚙️ 2. 설정 명령어 기반 핵심 작동 로직 (3대 메커니즘)

IPsec VPN은 무작정 연결되지 않고 **[대상을 고르는 눈] ➔ [안전한 대화방 개설] ➔ [데이터 암호화 수송]**의 3단계를 거쳐 작동합니다.

### 👁️ [Step 1] 무엇을 암호화할 것인가? (흥미 트래픽 감지)
```text
access-list 130 permit ip 192.168.10.0 0.0.0.255 192.168.20.0 0.0.0.255
```
* **로직:** 출발지가 서울 내부망이고 목적지가 부산 내부망인 패킷을 찾아 합격(Permit) 처리합니다.
* 이를 **흥미 트래픽(Interesting Traffic)**이라 부르며, 이 조건에 맞는 패킷이 인터페이스로 들어오는 순간 잠자고 있던 VPN 터널 가동 엔진이 작동합니다.

### 🤝 [Step 2] 1단계: 안전한 대화방 개설 (IKE Phase 1 / ISAKMP)
```text
crypto isakmp policy 1
 encr aes 256
 authentication pre-share
 group 5
crypto isakmp key gtech45 address 30.30.30.1
```
* `encr aes 256`: 임시 대화방의 내용을 해독이 불가능에 가까운 **AES-256** 알고리즘으로 암호화합니다.
* `authentication pre-share` & `key`: 미리 약속한 **비밀번호(gtech45)** 방식으로 신원을 인증합니다. 양쪽 라우터의 철자가 일치해야 터널이 형성됩니다.
* `group 5`: **디피-헬먼(Diffie-Hellman)** 수학 알고리즘을 사용합니다. 중간에 해커가 도청해도 R1과 R2만 똑같은 '임시 암호 키'를 수학적으로 만들어낼 수 있게 합니다. (1536비트 크기의 안전성)

### 📦 [Step 3] 2단계: 진짜 데이터 암호화 수송 (IKE Phase 2 / IPsec SA)
```text
crypto ipsec transform-set VPNSET esp-aes esp-sha-hmac
```
* `esp-aes`: 진짜 데이터를 포장할 때 **ESP(Encapsulating Security Payload)**라는 보안 봉투를 사용하고, 내용물은 **AES**로 암호화하여 원본 IP 주소를 완벽히 숨깁니다.
* `esp-sha-hmac`: **SHA** 해시 알고리즘을 사용해 데이터에 일종의 '디지털 지장'을 찍습니다. 데이터가 이동 중에 1비트라도 변조되면 즉시 폐기하여 무결성을 검증합니다.

## 🛠️ 3. 포트폴리오용 단계별 트러블슈팅 가이드

IPsec VPN 통신이 실패할 경우, 무작정 설정을 다시 보기보다 **Phase 1(인증) ➔ Phase 2(암호화 화물) ➔ 데이터 전송(실제 트래픽)**의 흐름에 따라 단계별로 접근해야 신속한 트러블슈팅이 가능합니다.

### 📊 1단계: 상시 확인 및 검증 명령어 (Show Commands)

#### ① `show crypto isakmp sa` (Phase 1 상태 확인)
* **목적:** 두 라우터 간에 신원 확인 및 임시 비밀 대화방(Phase 1)이 정상적으로 열렸는지 확인합니다.
* **정상 상태 확인 지표:** `State` 항목이 **`QM_IDLE`** 상태여야 합니다. 
* **트러블슈팅 팁:** 만약 이 값이 `MM_NO_STATE`이거나 비어있다면, 공인 IP 간에 통신(Ping)이 안 되거나 **Pre-Shared Key(비밀번호) 오타**가 발생한 경우입니다.

#### ② `show crypto ipsec sa` (Phase 2 상태 및 트래픽 확인)
* **목적:** 실제 사설 데이터가 암호화되어 터널을 통과하고 있는지 확인합니다.
* **정상 상태 확인 지표:**
  * `#pkts encaps / #pkts encrypt`: 내보낸 데이터가 암호화된 패킷 수 (통신 시 숫자가 올라가야 함)
  * `#pkts decaps / #pkts decrypt`: 받아온 데이터가 복호화된 패킷 수 (통신 시 숫자가 올라가야 함)
  * `current outbound spi`: `0x0`이 아닌 고유한 16진수 값이 할당되어 있어야 터널이 맺어진 것입니다.
* **트러블슈팅 팁:** 1단계는 `QM_IDLE`인데 이 숫자들이 모두 `0`으로 멈춰있다면, **Access-list(ACL 130)에서 대역 지정을 잘못했거나**, 내부 PC에서 상대방 내부 PC로 핑을 때리는 등의 **'흥미 트래픽'이 발생하지 않은 상태**입니다.

#### ③ `show crypto map` (종합 인터페이스 바인딩 확인)
* **목적:** 생성한 Crypto Map이 외부 가상 회선(인터페이스)에 정상적으로 적용되어 감시 중인지 확인합니다.
* **정상 상태 확인 지표:** `Interfaces using crypto map VPNMAP: Serial0/3/0` 형태로 정상 매핑되어 있어야 합니다.

---

### 🚨 2단계: 문제 분석을 위한 실시간 디버그 명령어 (Debug Commands)
*⚠️ 주의: 디버그 명령어는 장비에 부하를 주므로 현업 실무에서는 트래픽이 적은 시간에 제어하여 사용해야 합니다. 포트폴리오 작성 시 이 점을 명시하면 가점을 얻을 수 있습니다.*

#### ① `debug crypto isakmp` (Phase 1 상세 분석)
* **목적:** 비밀번호 인증 및 디피-헬먼 키 교환 과정의 에러를 실시간으로 추적합니다.
* **트러블슈팅 사례 (실제 발생했던 현상):**
  * 디버그 메시지 중 `ATTRIBUTES_NOT_MATCHED` 출력: 양쪽 라우터의 `crypto isakmp policy` 내 암호화 방식(`aes 256`)이나 그룹(`group 5`) 설정이 서로 다를 때 발생합니다.
  * `NOTIFICATION_AUTHENTICATION_FAILED` 출력: 양쪽 라우터의 **`crypto isakmp key` (비밀번호)가 불일치**할 때 발생합니다.

#### ② `debug crypto ipsec` (Phase 2 상세 분석)
* **목적:** 2단계 Transform-set 설정 오류나 ACL 미스매치를 실시간으로 확인합니다.
* **트러블슈팅 사례:** `IPSEC(validate_transform_proposal): transform proposal not supported`라는 에러가 뜬다면, R1과 R2의 `transform-set`(예: 한쪽은 esp-aes, 다른 쪽은 esp-3des 등) 정의가 서로 달라 데이터 협상에 실패한 상태입니다.

## 🔄 4. 요약: 데이터 전송 시 패킷 구조의 변화

서울 PC(`192.168.10.1`)가 부산 PC(`192.168.20.1`)로 `"안녕하세요"`를 보낼 때의 구조 변화입니다.

1. **라우터 내부 진입 시 (원본 패킷)**
   * `[출발: 192.168.10.1 | 도착: 192.168.20.1][데이터: 안녕하세요]`
2. **Crypto Map을 거쳐 인터넷으로 나갈 때 (VPN 암호화 패킷)**
   * `[새로운 공인 IP 헤더 (출발: 20.20.20.1 | 도착: 30.30.30.1)][ESP 보안 헤더][암호화된 영역: (원본 IP 헤더 + 안녕하세요)][ESP 테일러]`
3. **최종 처리**
   * 공인 인터넷망의 라우터들은 안의 진짜 내용을 모른 채 목적지 `30.30.30.1`로 배달하고, R2 라우터가 최종적으로 패킷을 열어 복호화한 뒤 사설망으로 전달합니다.
